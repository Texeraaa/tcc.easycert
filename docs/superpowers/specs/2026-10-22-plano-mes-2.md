### 2.2 Bloqueadores técnicos (B1–B3, decididos em 2026-10-22)

| # | Área | Decisão |
|---|---|---|
| B1 | Rate-limit | `@nestjs/throttler` global com default 60 req/min + override `@Throttle({default: {limit: 30, ttl: 60_000}})` em `GET /v/:codigo`. Memory store em dev; Redis store quando houver deploy. Lib única (não convive com `express-rate-limit`). |
| B2 | Mitigação CSRF | `csrf-csrf` (fork mantido do `csurf` deprecado). Double-submit cookie: middleware NestJS valida header `X-CSRF-Token` contra cookie `csrf-token` em todas as mutations (POST, PATCH, DELETE), exceto `POST /auth/login` no primeiro turno. Rota `GET /auth/csrf-token` emite o token. |
| B3 | Lib argon2 | `@node-rs/argon2` (binding Rust via napi-rs). Zero node-gyp, zero toolchain C nativo — funciona em alpine docker sem rebuild. Escolhida em detrimento de `argon2` (binding C via node-gyp). |

## 3. Arquitetura resultante

### 3.1 Backend (`apps/api`)

**9 módulos NestJS por entidade:**
1. **AuthModule** — Passport local + JWT strategy, guards JWT + Roles, rotas `/auth/login|me|logout|csrf-token`.
2. **UserModule** — CRUD de usuários (admin cria aluno/coordenador; aluno edita próprio perfil).
3. **SubmissionModule** — ciclo de estados `AWAITING_UPLOAD → PENDING → UNDER_REVIEW → APPROVED | REJECTED | CORRECTION_REQUESTED`.
4. **DocumentoModule** — versionamento de PDFs e emissão de certificados internos (com `codigo` + `revogadoEm`).
5. **AvaliacaoModule** — decisão do coordenador sobre uma submissão (acoplado a Submission).
6. **MatrizModule** — CRUD de `Categoria` + `RegraMatriz`, validação de tetos.
7. **EventoModule** — CRUD de `EventoInterno` (sem `Presenca` na v1 — pendência aberta).
8. **AuditModule** — service injetável, sem controller público. Chamado por outros services.
9. **NotificationModule** — interface `MailProvider` + `MailtrapProvider` + `FakeMailProvider`; chamado em cada transição relevante.

**Infra transversal (bootstrap em `main.ts` + `app.module.ts`):**
- `PrismaModule` global com `onModuleInit` chamando `$connect()`.
- `ConfigModule` com schema Zod validando `.env`.
- `ValidationPipe` global com `nestjs-zod`.
- `helmet()`.
- `@nestjs/throttler` global (60 req/min default; override em rotas específicas).
- Exception filter customizado anexando `request-id` em erros.
- `nestjs-pino` com redaction.
- Middleware `csrf-csrf` (double-submit).

### 3.2 Frontend (`apps/web`)

Next.js 15 App Router + React 19:
- **UI:** shadcn/ui + Tailwind + tokens de [[design/DESIGN]].
- **Middleware** (`src/middleware.ts`): lê cookie `easycert_session`; não-autenticado → `302 /login`.
- **Helper `apiFetch()`** server-side: lê cookie do request Next via `cookies()` de `next/headers` e repassa como header `Cookie` ao `fetch()` da API. Centraliza também o header `X-CSRF-Token` em mutations.
- **Páginas (half-circle aluno):**
  - `/login` — form shadcn (email + senha), POST para `/auth/login`, redireciona para `/aluno`.
  - `/aluno` — home autenticada, mostra nome + CTAs (nova submissão, listar).
  - `/aluno/submissoes/nova` — form (categoria, carga informada, instituição) + input file. XHR direto para MinIO via POST policy; no sucesso, chama `POST /submissions/:id/confirm`.
  - `/aluno/submissoes` — tabela com estado, data, link PDF, paginação cursor-based.
  - `/aluno/submissoes/[id]` — detalhe + histórico de estados + motivo de indeferimento se houver.

### 3.3 Infra local (`docker-compose.yml`)

- **Postgres:** volume `postgres_data`. Script de init SQL cria dois roles: `easycert_owner` (owner do schema, usado por migrations) e `easycert_app` (usado pela aplicação em runtime). Duas `DATABASE_URL` no `.env`.
- **MinIO:** volume `minio_data`, porta 9000. Serviço `minio-init` roda após healthcheck do MinIO.
- **Mailtrap:** credenciais via `.env.local` (sem container local).

### 3.4 Variáveis de ambiente (`.env.local`)


**Nota:** `PORT=3333` é optional (código default já é 3333); `WEB_ORIGIN` idem. `DATABASE_URL_MIGRATE` só é lido por `pnpm db:migrate` (execução offline). **Sem bloqueadores Mês 2** — matriz FMPFM e regulamento de horas complementares foram movidos para "A confirmar" com data-limite Mês 4.

### T4 — Schema Prisma + migrations [depende de T1]

- **T4a** — `User` enriquecido com campos `id: UUID`, `email: String UNIQUE`, `passwordHash: String`, `nome: String`, `dataIngresso: Date`, `matricula: String?`, `curso: String?`, `ativo: Boolean`, `role: Role` (enum `ALUNO | COORDENADOR | ADMIN`). Índice unique em `(email)`, índice regular em `(role, ativo)` para queries de listagem admin.
- **T4b** — `Categoria` + `RegraMatriz` (tabela normalizada, campos Q4).
- **T4c** — `Submission` (ciclo completo de estados) + `Documento` (`codigo` UUIDv4, `revogadoEm`, `version`, `storageKey`, `confirmedAt`, `tipo` enum) + `Avaliacao`.
- **T4d.a** — `AuditLog` modelo Prisma (`id`, `actor`, `action`, `entityType`, `entityId`, `before: Json`, `after: Json`, `reason: String?`, `createdAt`).
- **T4d.b** — Migration SQL manual: `REVOKE UPDATE, DELETE ON audit_log FROM easycert_app`. Ajuste `docker-compose.yml` para criar os dois roles no init SQL; adicionar segunda `DATABASE_URL` ao `.env.local`.
- **T4e** — `EventoInterno` (campos: `id`, `titulo`, `descricao`, `data`, `cargaHoraria`, `categoriaId`, `organizadorId`, `createdAt`). Sem `Presenca` na v1 (pendência aberta).

### T5a — Infra backend NestJS [depende de T4a]

Bootstrap em `main.ts` + `app.module.ts`:
- `PrismaModule` global com `onModuleInit` chamando `$connect()`. Dois `DATABASE_URL` via `ConfigService`: `DATABASE_URL` em runtime, `DATABASE_URL_MIGRATE` para migrations (isolado).
- `ConfigModule` com Zod schema do env — validar presença de `JWT_SECRET`, `CSRF_SECRET`, porta (default 3333), `WEB_ORIGIN` (default `http://localhost:3000`).
- `ValidationPipe` global via `nestjs-zod` — rejeita payloads desconhecidas (`forbidUnknownValues: true`).
- `helmet()` middleware para security headers.
- `@nestjs/throttler` instalado + global default 60 req/min com memory store (dev). Decorator `@Throttle({...})` em rotas específicas (ex: `GET /v/:codigo` = 30 req/min).
- Exception filter customizado que capetura erros não-tratados e anexa `X-Request-Id` ao response (obtido de `AsyncLocalStorage` do middleware de request-id).
- Middleware `request-id`: gera UUID por request, armazena em `AsyncLocalStorage` (acessível em qualquer serviço downstream), inclui no response header `X-Request-Id`.
- Middleware `csrf-csrf` (double-submit cookie) aplicado globalmente a mutations. **Rotas exempt:** `POST /auth/login` (primeiro turno, sem cookie CSRF ainda), `POST /auth/logout` (cookie pode estar expirado), `GET /auth/csrf-token` (GET é isento por natureza; listado para clareza). Fluxo primeiro-login: cliente POSTa em `/auth/login` sem CSRF → sessão criada → GET `/auth/csrf-token` seta cookie `csrf-token` → mutations seguintes incluem header `X-CSRF-Token`. Ratificado em 2026-10-22.

### T5b — Observabilidade [depende de T5a]

- `nestjs-pino` instalado e wire como logger default.
- Middleware `request-id` com `AsyncLocalStorage`.
- Rotas `/health/live` e `/health/ready`.
- Redaction configurado em `nestjs-pino`.
- Exception filter inclui `X-Request-Id` no response header.

### T5d — DTOs Zod em `@easycert/types` [paralelo com T5a-b]

Convenção: `packages/types/src/<domain>/<entity>.schema.ts` exportando `const FooSchema = z.object(...)` + `type Foo = z.infer<typeof FooSchema>`. Backend consome via `createZodDto(FooSchema)`; frontend via `@hookform/resolvers/zod` + inferência de tipo.

Schemas iniciais mínimos: `LoginDto`, `CreateSubmissionDto`, `ConfirmSubmissionDto`, `SubmissionResponseDto`.

**Importante:** T5d precisa estar pelo menos iniciado antes de T5e começar (controllers consomem schemas).

### T5e — Módulos NestJS stub [depende de T5a + T5b + T5d]

Quebrado em 4 subtarefas por acoplamento de domínio (recomendação `tech-architect` I1):

- **T5e.1 — AuthModule + UserModule** (core, bloqueia T6). Strategies local + JWT, guards, controller `/auth/*`. `UserService` com CRUD stub.
- **T5e.2 — SubmissionModule + DocumentoModule + AvaliacaoModule** (fluxo acoplado, bloqueia T7). Três services com `findById`, `create`, `update` stub. `DocumentoModule` já contém a rota pública `GET /v/:codigo` com `@Throttle` override.
- **T5e.3 — MatrizModule + EventoModule** (admin, pode rodar em paralelo com T5e.2 depois de T5e.1 fechar).
- **T5e.4 — AuditModule + NotificationModule** (cross-cutting). `AuditModule` decorado com `@Global()` — `AuditService` expõe `log({ actorId, action, entity, entityId, metadata? })` injetável em qualquer outro service sem import explícito. **Assinatura usa primitivos** (nunca entidade Prisma) para evitar dependências circulares com `UserService` e similares. Ambos chamados pelos demais modules (ex: `SubmissionModule` injeta `AuditService` + `MailProvider` para disparar notificações de transição).

### T6 — Fluxo E2E 1: Autenticação [depende de T4a + T5a-f + T5e.1]

**Backend:**
- `POST /auth/login` — valida `email + senha` com `argon2.verify`, emite JWT, `res.cookie('easycert_session', jwt, {httpOnly: true, sameSite: 'lax', secure: isProd})`.
- `GET /auth/me` — retorna usuário autenticado a partir do JWT no cookie.
- `POST /auth/logout` — `res.clearCookie('easycert_session')`.
- `GET /auth/csrf-token` — emite token para o frontend injetar nas próximas mutations.
- `JwtAuthGuard` + `RolesGuard` + decorator `@Roles('ALUNO' | 'COORDENADOR' | 'ADMIN')`.
- Audit via Pino (login/logout **não** entram em `AuditLog`).

**Frontend:**
- `/login` — form shadcn com validação Zod (`LoginDto`); POST para `/auth/login`.
- `/aluno` — home autenticada, mostra `nome` do aluno via `GET /auth/me`.
- Middleware aplica redirect; `apiFetch` server-side repassa cookie em RSC fetches.

**Teste manual:** fluxo completo em dev — abrir `/aluno` sem login → redireciona `/login` → logar → vai para `/aluno` com nome do aluno.

### T7 — Fluxo E2E 2: Submissão com upload direto [depende de T4c + T5e.2 + T5e.4 + T6 + T7a]

**Backend:**
- `POST /submissions` — cria `Submission` em `AWAITING_UPLOAD`, usa `@aws-sdk/client-s3` `createPresignedPost` com `Conditions: [["content-length-range", 0, 10485760], ["eq", "$Content-Type", "application/pdf"]]`. Retorna `{ submissionId, upload: { url, fields, key } }`.
- `POST /submissions/:id/confirm` — faz `HeadObject` + `GetObject` com `Range: bytes=0-7` no bucket, valida magic bytes `%PDF-`, transita para `PENDING` ou `UPLOAD_INVALID`. Audit log `submission.state_changed`.
- `GET /submissions/me` — lista submissões do aluno autenticado, cursor-based.
- `GET /submissions/:id` — detalhe + histórico de estados.

**Frontend:**
- `/aluno/submissoes/nova` — form (categoria select, carga numeric, instituição text, input file accept `.pdf`). Submit: (1) `POST /submissions` → recebe presigned POST, (2) XHR direto para MinIO com os `fields` + o arquivo, (3) `POST /submissions/:id/confirm`.
- `/aluno/submissoes` — tabela com `estado`, `data`, link para PDF.
- `/aluno/submissoes/[id]` — detalhe + histórico + motivo de indeferimento (se existir).

**Teste manual:** upload end-to-end de um PDF válido do browser até `PENDING`; depois upload de arquivo que não é PDF (bytes ≠ `%PDF-`) → `UPLOAD_INVALID` com UX de reenvio.

## 5. Riscos conhecidos e mitigações

| Risco | Mitigação |
|---|---|
| Binding nativo de argon2 quebra em CI/alpine | `@node-rs/argon2` via napi-rs — zero node-gyp. |
| Cookie HttpOnly + fetch RSC server-side não propaga sozinho | Helper `apiFetch()` server-side lê `cookies()` de `next/headers` e repassa como header `Cookie`. |
| `prisma migrate reset` em dev recria `audit_log` sem REVOKE | Dois roles distintos: `easycert_owner` roda migrations (cria tabela), migration SQL manual aplica REVOKE em `easycert_app`. Reset executa migrations em ordem; REVOKE reaplicado. |
| Rate-limit em memória não escala | Memory store OK para Mês 2 (dev + TCC); Redis store entra apenas se houver deploy multi-instância. |
| CSRF implementado errado | Usar lib `csrf-csrf` (fork mantido, auditado) com double-submit cookie, não implementação custom. |
| (Débito #6) Prisma shutdown sem `$disconnect()` | T5a inclui `PrismaService` implementando `OnModuleInit` + `OnModuleDestroy` com `$connect()`/`$disconnect()` + `app.enableShutdownHooks()` em `main.ts`. Fecha conexões limpas no SIGTERM — relevante para `/health/ready` responder correto durante shutdown. |
| (Débito #7) Migration SQL REVOKE aplicada à parte | Migration de REVOKE no `audit_log` é **versionada em Prisma** (nome `YYYYMMDDHHMMSS_make_audit_log_immutable`), não aplicada via `psql -c` solto. Garante idempotência, rastreabilidade e que `prisma migrate reset` reaplica a invariante. Mitiga risco de `audit_log` ficar mutável silenciosamente. |
